# Dispatch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and deploy Dispatch, an event-driven support ticket system (users raise tickets, admins resolve them) with a persistent event pipeline and an Event Inspector.

**Architecture:** Modular-monolith Express + Postgres API. Domain changes write an `events` row in the same transaction (outbox); an in-process dispatcher runs handlers and records each run in `event_deliveries` with retry/backoff. A Vite React app is served by the same Express process (one origin, one Docker image).

**Tech Stack:** Node 20+, TypeScript, Express, Prisma, Postgres, Zod, argon2, jsonwebtoken, helmet, express-rate-limit, pino; Vitest + Supertest; React, Vite, Tailwind, shadcn/ui, Geist, Lucide, TanStack Query, React Router, Framer Motion; Docker; Render + Neon.

**Spec:** `docs/superpowers/specs/2026-11-26-dispatch-design.md` (source of truth: `Assignment.pdf`).

## Global Constraints

- Backend is Node.js + Express + TypeScript; DB is Postgres; frontend is React (Vite). One deployable, same-origin.
- No Redis, Kafka, RabbitMQ, microservices. Events are DB-backed; never rely only on `EventEmitter`.
- Layering: routes parse/validate only; services hold rules and authorization; Prisma only in services/repositories.
- Error shape everywhere: `{ "error": { "code": string, "message": string, "details"?: unknown } }`. Codes: `VALIDATION_ERROR` 400, `UNAUTHENTICATED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409, `RATE_LIMITED` 429, `INTERNAL` 500.
- Register creates only `USER`. Admins come from the seed script only.
- Another user's ticket returns 404 (never 403). Users cannot change status. Users edit/delete only while ticket is `OPEN`; delete is soft (`deleted_at`).
- JWT in httpOnly, SameSite=Lax cookie named `dispatch_token`, `Secure` in production; 1h expiry.
- `STATUS_CHANGED` and `TICKET_RESOLVED` are both emitted when status becomes `RESOLVED`. Event types: `TICKET_CREATED`, `TICKET_UPDATED`, `STATUS_CHANGED`, `COMMENT_ADDED`, `TICKET_RESOLVED`. Handlers: `activity`, `notification`, `email` (logging stub).
- Visual language: obsidian surfaces, subtle violet accent, Geist, Lucide. One design system, two layouts (admin split-pane, user portal).
- Commit after each task. Every task leaves `npm test` green.

## Review Focus

Inputs and conditions the spec implies but doesn't spell out; each has a pinning test in the owning task.

1. Email case/whitespace (`A@x.com` vs `a@x.com ` registering twice) → second register is `CONFLICT`, login works case-insensitively. (Task 2)
2. Malformed ticket id (`/api/tickets/not-a-uuid`) → 404, never 500. (Task 4)
3. Absurd pagination/sort (`limit=100000`, `page=-1`, `sort=password`) → clamped or 400, never a crash or unlisted-column sort. (Task 4)
4. Handler throws → ticket change still committed; delivery `FAILED`, retried, then `DEAD`. (Task 6)
5. Same status set twice, or two concurrent resolves → exactly one `STATUS_CHANGED`/`TICKET_RESOLVED` pair. (Task 4)
6. Tampered/expired cookie, and a deleted user's still-valid token → 401. (Task 2)
7. Whitespace-only title/comment body, and oversize text (title >120, description/body >5000) → `VALIDATION_ERROR`. (Tasks 4, 5)

### Task 6: Dispatcher, handlers, notifications

**Files:** Create `server/src/modules/events/{dispatcher,handlers}.ts`, `server/src/modules/notifications/{routes,controller,service}.ts`, `server/test/dispatcher.test.ts`, `server/test/notifications.test.ts`. Modify `index.ts` (start dispatcher; stop on SIGTERM), ticket/comment services (call `nudge()` after commit).

**Interfaces:**
- Consumes: `recordEvent` rows, `config.maxDeliveryAttempts`.
- Produces: `type Handler = (event: Event) => Promise<void>`; `handlers: Record<HandlerName, Handler>` (exported, mutable so tests can swap one); `dispatchDue(now?: Date): Promise<number>` (claims due `PENDING|FAILED` deliveries with `FOR UPDATE SKIP LOCKED` in a transaction batch, runs each handler, records `SUCCEEDED` with `durationMs`, or `FAILED` with `attempts+1`, `lastError`, `nextAttemptAt = now + 5s * 2^attempts`, or `DEAD` when attempts reach max; returns count processed); `startDispatcher(): () => void` (interval = `config.dispatcherIntervalMs`, returns stop fn); `nudge(): void` (fire-and-forget `dispatchDue`, errors logged, never thrown into request path); `retryDelivery(id): Promise<void>` (sets `PENDING`, `attempts=0`, `nextAttemptAt=now`).
- Handlers: `activity` logs a structured pino line (timeline reads `events`); `email` logs a "would send" line; `notification` inserts `notifications` rows idempotently (unique `(userId, eventId)`). Recipient rules: ticket owner is notified of admin-actor events (`STATUS_CHANGED`, `TICKET_RESOLVED`, admin `COMMENT_ADDED`); all admins are notified of `TICKET_CREATED` and user-authored `COMMENT_ADDED`; the actor never notifies themselves; `TICKET_UPDATED` notifies the other party.
- Notifications routes: `GET /api/notifications` (own, newest first, `unreadCount`), `PATCH /api/notifications/:id/read` (own only, else 404), `POST /api/notifications/read-all`.

- [ ] **Step 1: Write failing tests:** `dispatchDue` marks all three deliveries `SUCCEEDED` with `durationMs ≥ 0` for a fresh `TICKET_CREATED`; swap `handlers.email` to throw → that delivery `FAILED`, attempts 1, `lastError` set, `nextAttemptAt` in the future, **the ticket still exists** (Review Focus 4); not picked up before `nextAttemptAt`, picked up after (pass `now`); after max attempts → `DEAD` and never re-run; running `dispatchDue` twice concurrently (`Promise.all`) executes each handler once; re-running a succeeded delivery's handler doesn't duplicate notifications; `retryDelivery` revives a `DEAD` one; notification recipient rules above (one test per row); user cannot read or mark another user's notification.
- [ ] **Step 2-4:** Run FAIL → implement → PASS.
- [ ] **Step 5:** Manually run the server, create a ticket via curl, confirm deliveries become `SUCCEEDED` without calling `dispatchDue` by hand.
- [ ] **Step 6:** Commit `feat(events): dispatcher with retry, handlers, notifications`.

**Acceptance:** failures are isolated, retried, dead-lettered and visible in the DB; notifications follow the recipient rules.
